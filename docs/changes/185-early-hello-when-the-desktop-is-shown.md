# 185 - Early hello: the greeting plays the moment the desktop is shown (2026-11-02)

Plan: docs/features/158-early-hello-and-session-reopen-plan.md (P-1 + P0). Coded by Claude: the owner asked for GLM 5.3 Flash through OpenCode, but OpenCode answered "Free usage limit reached" (three attempts produced no files), and the owner chose "I code it".

## Built
- `early_hello.rs`: a thread started at the top of `run()`, ONLY for the logon-task launch (`--background`) and when `earlyHello` (default true, in `NexusSettings`) is on. It waits (up to 90 s) until the DESKTOP is shown: the input desktop is the normal "Default" one (the logon animation and the lock screen are on "Winlogon"), the taskbar window is visible and the desktop window is visible; after 250 ms it plays the cached clip of the user's edge voice for the part of the day (morning 05-11:59, afternoon 12-17:59, evening 18-21:59, night 22-04:59; night uses the evening clip until new clips exist) through rodio at 85 % volume, retrying the audio device for 10 s. No clip, no device or no desktop -> it gives up quietly and the normal hello speaks as before.
- `hello_script.json` (app data): voice, lines per part of the day, last variant, last played; a variant is never repeated back to back; at most one early hello per 2 h; a voice change keeps `last_played`.
- The normal boot hello (`memcore::briefing::submit_hello`) stays silent while the early one is waiting or has played, and records `last_hello_ts`.
- Boot marks: `setup_before_tray`, `early_hello_desktop_shown`, `early_hello_audio` (see `boot_timeline.jsonl`) to measure the 13.5 s tray gap and the real time to sound.

## Update 2026-11-02 (d): the 20:35 logon test (no orb, 15-20 s to "Welcome back")
Two independent passes (the main investigator and an Opus second opinion, `docs/research/early-hello/04-logon-2026-11-02-second-opinion.md`):
- **Cause 1 (confirmed, high confidence): the early hello had nothing to play.** The logon was the first run of a binary that added "Welcome back, sir"; its clip was not on disk (the log shows Edge synthesising it at 20:35:56), so `run()` returned before waiting for the desktop. My first guess (the 2 h rule) was WRONG: `hello_script.json` on disk was version 1, so `load_script` started with no `last_played`. Side bug found: a version bump dropped `last_played`.
- **Cause 2: the stage window took 21.4 s** (7.7 s and 8.3 s at earlier logons) on the setup thread; the normal hello waits for the stage, hence ~33 s. The tray then took 7.3 s (it took 18.7 s when the stage was fast): the same fixed logon stall (Explorer start, PowerToys, Defender, other installs) lands on whichever step is running; setup ended ~45-47 s after OS start both times. EcoQoS is not inherited by WebView2 and was on at the fast logons: at most a contributor (A/B with `NEXUS_NO_ECOQOS=1`, 3+ logons each).
- **Why we could not see it**: `println!` output has no destination in the console-less release exe.
- **Fixed now**: (1) never silent for lack of a clip: the picked line, else another line of the same part of the day, else the always-cached "Hello, sir"; (2) `load_script` keeps `last_played` across a format change; (3) every way the early hello ends without speaking writes a `early_hello_gave_up` boot mark with the reason (plus `early_hello_playing`), and stdout/stderr are redirected into `logs/nexus.log` so `[EARLY-HELLO]` / `[BOOT]` lines are visible. Tests added; Rust lib suite passes.
- **Not fixed yet**: the stage window and tray are still created one after the other on the setup thread (would overlap the stalls, est. 7-9 s faster app readiness); the normal hello still waits for the stage; the memory store cannot be decrypted ("wrong key or corrupt file", every run since 14:41 IST, cause unknown; `last_hello_ts` and the saved session offer depend on it; back up `memcore.enc` before any recovery).
