# Nobody owns loading state: give it one owner

NEXUS has no single owner of the loading state, and the current design is not good enough. The main command center (`center.rs`) validates and routes turns but does not decide loading. A purpose-built guard for it, `center::direct_ui(UiDirective::Loading)`, has **zero callers**, and `loading_should_show` is dead code used only in tests (`D:\ULTRON\src-tauri\src\center.rs:725-759`). In practice the decision is spread across about six hand-written blocks in `orchestrator.rs`, a second state machine in the frontend (`store/assistant.ts`, `loadingMachine.ts`, roughly 30 `setLoadingVisible` writers), and an `OrbFrame.tsx` effect that echoes frontend state back into Rust. The result is duplicate show/hide pairs in the real log and an orb whose fate depends on timers that do not agree. The supplied log does **not** reproduce the orb vanishing at an ack: both logged ack turns ("One moment sir.", "Working on it sir.") kept the orb on screen throughout. The vanishing orb is therefore a code-derived hypothesis, not an observed fact. The code does contain several concrete paths that make it happen. I recommend neither a new "super-center" that owns state nor leaving things as they are. The fix is a single derived presentation layer, with the orchestrator as the only writer of "a turn or task is pending" and the audio player as the only signal that speech has ended. That matches how the comparable open-source assistants are built.

## What the code does today

The only loading primitives are `show_loading` and `hide_loading` (`orchestrator.rs:9997-10025`). They emit `stage:loading_visible` and `stage:loading_rect`. `show_loading` refuses to act when there is no active request or when a ghost session is running. `hide_loading` has no guard and no request id, so a hide for one turn can hide another turn's spinner. Each subsystem branch in `process_transcript` pairs these calls by hand with an `OrchestratorEvent::Loading` and an `Ack`. Those branches are WorkerBackend (lines 2231-2291), GitHub (2484-2591), MCP read operations (2785-2843), compound plans (9397-9446), and the screen tour and reverse-engineer runners. The Architect branch shows loading and never hides it in Rust, relying on the frontend instead. A comment at `orchestrator.rs:775-779` states the intent that loading is decided "per turn from events, not enums". That is a design choice, but nothing enforces it.

Many long-running runners have no loading handling at all. That includes foreground review, coding-agent tasks, watch-agent tasks, screen analysis, directions, and the CodeRabbit and AI-review voice paths. The notes call this an absence found by grep. They did not check whether each runner emits its own State or Ack elsewhere. The extreme case is background work that outlives the turn. `coderabbit_review::start_review` spawns a job that runs 2-15 minutes and ends the turn with `say_and_finish`. It then clears the request, so a later `show_loading` would be rejected by its own guard. The only signal is a proactive spoken line at completion (`coderabbit_review.rs:461-490`). The frontend's 120 s loading failsafe would also contradict a 15-minute spinner. This is a separate concept from the turn spinner and nobody owns it.

The frontend duplicates the state. The Zustand store runs a loading state machine with an 800 ms minimum dwell, and `OrbFrame.tsx:656-665` calls `orchestrator_show_loading` or `orchestrator_hide_loading` whenever that store value changes. The real log shows the symptom. Each turn has two "loading indicator shown" lines about 12-15 ms apart and a second "hidden" line about 170 ms after the Rust one (`nexus_unified.log`, request `adf342d98b46`, around 20:20:00.28 to 20:20:01.09). The spinner is also rendered by `LoadingIndicator.tsx`, which listens to raw stage events and never reads the store. Two clients therefore drive one element, and neither knows the other's state.

## Why the orb disappears or sits in a wrong state

The code review found that the intended design and the implemented design contradict each other. The comments say the ack plays, the orb disappears, and the spinner carries the turn (`net/orchestrator.ts` lines 541-544, 563-564, 579-580). After the "never hide while speaking" rewrite, `hideOrbAfterSpeech` only hides when the store state is `idle`. In the ack window the state is `thinking` or `speaking`, so the hide chains are effectively no-ops on the plain Worker, MCP and GitHub paths. A held-over thinking dwell (1 s) delays the ack's state change, and the chain started by `Loading(true)` fires while the store is still `thinking` and simply ends. The ack's own chain finds `speaking`, polls, and at ten ticks calls `finishSpokenResult(getCurrentRequestId() ?? "")`. During the ack phase `currentRequestId` is still `null`, so that call does nothing. The practical effect on these paths is the opposite problem: the orb stays up in a silent "speaking" pose beside the spinner, because nothing returns the state to `thinking` after the ack (the legacy `wsBridge.ts` handler did that; the Rust-orchestrator path does not).

The orb does vanish early on paths where the ack is delivered as a `Result`. Examples are the screen tour (Ack, then `speak_line`, then `Loading(true)`), the "Give me a minute, sir." slow notice that fires after 6 seconds, CodeRabbit's working lines, and reverse-engineer. On those paths the frontend `result` handler speaks the line, and `finishSpokenResult` sets the store back to idle and signals `orchestrator_done`, which clears the Rust request. The idle watchdog or the next hide-chain tick then hides the orb about 0.5-2.5 s later (`IDLE_HIDE_MS = 2500` in `orbIdleWatchdog.ts`). The same call clears the store's loading flag, which round-trips to `orchestrator_hide_loading`, and the Rust `show_loading` guard now rejects re-showing. The user would see no orb and no spinner while the tour or review is still being fetched. The notes mark this as code-derived; the supplied log contains no tour or CodeRabbit turn.

Other contributors are real but secondary. In the log, both ack turns were actually ended by a second Ctrl+Space press, and an `orb:cancel` produced `[ORB] visible=false`. That is by design, since the hotkey toggles cancel when the agent is active (`cdp_unified.log`, roughly lines 354-364 and 411-428), and it is the strongest candidate for a user seeing the orb vanish mid-ack. Two recovery guards are inert: `speechBecameAudible` is set true by the first `tts:playback_started` and never reset, so the 4 s silent-hide observer and the 2 s ack-deadline guard stop working after the first utterance of a session. The `stuckSpeakingTicks` counter is shared across concurrent hide chains, so two live chains halve the intended 10 s limit. The non-native recorder path for `open_architect` hides the orb after a fixed 1200 ms and then asks for a spinner that the Rust guard rejects as an orphan, but that path only runs for non-native transcripts, not normal mic turns. The speech arbiter silently drops an ack when anything else is active, and a result ack arriving within 600 ms cancels the deferred ack entirely. None of these were observed in the supplied log.

## Is a separate center needed?

The comparable systems say one lifecycle owner plus subscribers, not a second owner. Home Assistant Assist publishes pipeline events and a satellite state of IDLE, LISTENING, PROCESSING or RESPONDING. Its RESPONDING-to-IDLE transition is deliberately manual: the device must call `tts_response_finished`, because only the device knows when playback ended ([HA Assist satellite entity](https://developers.home-assistant.io/docs/core/entity/assist-satellite)). LiveKit Agents publishes one `lk.agent.state` attribute (initializing, idle, listening, thinking, speaking) and tells frontends to use boolean getters rather than raw states ([LiveKit agent state](https://docs.livekit.io/frontends/build/agent-state/)). Pipecat emits `BotStartedSpeaking` and `BotStoppedSpeaking` from the output transport, the component that plays the audio, not from the LLM stage ([Pipecat system frames](https://docs.pipecat.ai/server/frames/system-frames)). None of these has a first-class ack state; the ack is just output inside the processing state. OVOS is the distributed counterpart: skills write GUI state to namespaces and a service holds it ([OVOS GUI service](https://openvoiceos.github.io/ovos-technical-manual/104-gui_service)). NEXUS today resembles that second pattern, with the added defect that two writers drive the same element.

Two caveats limit how far this evidence goes. The inference that visibility should be a pure function of lifecycle state is the research notes' own reasoning, not a documented consensus; the notes found no write-up of a vanishing-avatar bug class. The notes also could not verify any Siri, Microsoft or current Google rule on ack timing. On latency, the usable thresholds are Nielsen's 0.1 s, 1 s and 10 s limits, which are a 1993 synthesis rather than a fresh experiment ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). Alexa permits up to five progressive responses before the final answer within an overall window of about 8 s, and drops a late ack ([Alexa progressive response](https://developer.amazon.com/docs/custom-skills/send-the-user-a-progressive-response.html)). For tasks that outlive the turn, Alexa moves completion out of band with a notification the user asks to have read ([Alexa ProactiveEvents](https://developer.amazon.com/en-US/blogs/alexa/alexa-skills-kit/2018/12/proactiveeventsapi-launch-announcement)). My verdict is that the main command center should not become the loading owner. It is a validator and router, and `direct_ui` is the right seat for the Rust side only if it becomes the single writer of "turn pending". A new "feedback center" connected to every sub-center would add a second writer, which is the anti-pattern. What is missing is one derived presentation function and one background-task concept distinct from the turn.

## Ordered, low-risk plan (no code changed yet)

The order is chosen so each step is independently shippable and reversible, starting with observation.

Step 1 adds logging only. In `net/orchestrator.ts`, `hideOrbAfterSpeech`, the `loading` and `ack` handlers, and `store/assistant.ts` `setVisible`, log the caller and request id on every `setVisible(false)` and on each hide-chain exit. In `orchestrator.rs`, `hide_loading` should log the active request id. Then capture a screen tour, a CodeRabbit voice start and a slow Worker turn. The discriminator from the notes is whether the CDP log shows `idle watchdog: hide` or `hideOrbAfterSpeech: speech and caption finished` within 3 s of the ack, and only one "loading indicator hidden" before the Result. This either confirms or kills the Result-style-ack hypothesis before any behaviour changes.

Step 2 fixes the cheap, clearly wrong state bugs. Reset `speechBecameAudible` per turn in `net/orchestrator.ts` (lines 69, 77, 105, 881-883), so the ack-deadline guard and the silent-hide observer work again. Make `stuckSpeakingTicks` per-chain, or cancel the previous chain when a new one is armed. Give `hide_loading` and the frontend hide effect a request-id check so a stale hide cannot touch a newer turn.

Step 3 removes double ownership of the spinner. In `OrbFrame.tsx:656-665`, stop echoing store changes into `orchestrator_show_loading` and `orchestrator_hide_loading`. Rust events become the only driver of the stage spinner and the store keeps only its own view. The duplicated lines in the log are the acceptance check, but confirm that no Architect or local flow relied on the echo, because the Architect branch has no Rust hide.

Step 4 introduces one derived visibility function in the frontend, for example `orbVisible = f(state, loadingVisible, pendingTask, ttsActive, captionActive, ghostActive)`. Route `idle watchdog`, `hideOrbAfterSpeech` and the ack handlers through it rather than calling `setVisible(false)` directly. Decide explicitly what the orb should do during a long wait: stay with the spinner, or hand over to it. Today's comments and code disagree. Also keep the end-of-speech transition driven by the audio player, as in the HA handshake.

Step 5 makes the main center the Rust-side seat. Call `center::direct_ui(UiDirective::Loading)` from `process_transcript` in place of the hand-written Ack and Loading pairs, one subsystem at a time (WorkerBackend first, then GitHub, MCP, compound). Remove the dead `#[allow(dead_code)]` marker only once it has callers. Stop `finishSpokenResult` from clearing the request for `speak_line` acks that precede continuing work, for example by marking the Result as an interim ack so the turn stays open for the tour and CodeRabbit paths.

Step 6 gives background tasks their own concept. Add a task chip or card tied to the existing job maps in `coderabbit_review.rs` and `ai_review.rs`, with its own lifecycle independent of the turn and of the 120 s failsafe. Completion keeps using `proactive_policy`. Do not reuse the turn spinner, whose guards reject post-turn shows.

## What to test and what stays unverified

Test with pure unit tests where possible: the derived visibility function and `loading_should_show` as table tests; `hideOrbAfterSpeech` with fake timers across thinking, speaking and idle; request-id-guarded hide; and a regression test that a Result-style ack does not clear the active request. The existing frontend suite (vitest, about 697 tests per `AGENTS.md`) and the Rust lib suite should stay green, and the dead-code ratchet should shrink. Live checks, which the owner must run because runtime and builds are owner-controlled, are: a screen tour, a CodeRabbit review start, a deliberately slow Worker turn (over 6 s, to hear "Give me a minute, sir."), a hotkey press during an ack, and a ghost-mode turn. Each should be judged against the CDP log lines above.

Unverified items: no logged turn took more than about 1 s, so every long-turn behaviour here comes from reading code. The notes did not read all `end_tour_fetch` callers, all of `reverse_engineer.rs`, or every frontend clear site. They did not check which long-running runners emit their own State or Ack, and they did not read the user's `settings.json` placement values for the orb and spinner. The one reproduction attempt in the supplied log did not show the orb vanishing at an ack, so the leading explanations (Result-style acks, hotkey barge-in) remain hypotheses until Step 1 produces evidence.

## Conclusion

The question "is the main center the decider" has a sharper answer than yes or no: it was meant to be, the hook exists, and nobody uses it. The loading state is decided by whoever wrote the nearest branch, and the frontend then re-decides it. The most useful finding is that the orb problem is likely two distinct failures that look alike. On plain Worker, MCP and GitHub acks the orb tends to stay up too long in a silent speaking pose, while on Result-style acks it hides early and can take the spinner with it. A single patch to the hide timers would fix at most one of them.

Going forward, the cheapest durable improvement is subtractive: remove the echo, guard hides by request id, and route visibility through one function, before adding any new component. The comparable assistants reach their reliability the same way, with one lifecycle owner, passive subscribers and an end-of-speech signal from the audio side. Start with the logging in Step 1, because a single captured tour or CodeRabbit turn will settle which hypothesis the plan should prioritise.
