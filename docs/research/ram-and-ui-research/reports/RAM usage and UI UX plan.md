# Taming NEXUS memory and unifying its two themes

NEXUS is light on memory in daily online use and inconsistent in look. Its biggest UI defect is that light theme is only half built. **Idle RAM is about 236 MB resident (269 MB commit)**, which is far below the 600-700 MB goal. The ceiling is only reached offline, when the local Kokoro voice (+360-400 MB) loads, and it is far exceeded if the Python speech fallback or several windows join in. Memory (memcore) is small, about 0.84 MB on disk and an estimated 2-5 MB in RAM. It is cheap to read but wasteful to write: each cloud turn reseals the whole file 3-5 times. On the UI side, the app runs **at least seven separate colour-token systems**, five different dock-button implementations, and several recent surfaces that are fixed dark with no light variant. Light-mode failures include invisible dock buttons, a black pebble orb that probably vanishes, white-on-near-white headings, and a CodeRabbit panel that stays dark. Every RAM figure is 13 days old (measured 2026-10-16/17) and NEXUS was not running when this was checked. Several UI surfaces could not be rendered, so the statements marked INFERRED below need a live check before work is scheduled. The plan (section 4) goes: tokens and theme switching first, then dock buttons, then each surface, then stage geometry, then accessibility and test gates, with RAM measurement running in parallel.

**Against the 600-700 MB goal.** Idle online is about 236 MB; a normal online turn is 290-350 MB. Online with the Hub open is about 385-575 MB, which is under the goal but near its top. Offline with Kokoro speaking is about 640-680 MB (the docs say 650-730), so it sits at or just over the ceiling. Offline with the Moonshine fallback active as well is roughly 990-1,070 MB, and "everything on" is 1.1-1.6 GB. The owner has said 700 MB is a goal and not a hard cap, and that speed beats RAM. The top four memory findings follow.

- Kokoro is the single big item (about 300-400 MB) and the only large one that is both measured and unloadable. The real log confirms the unload runs ("Kokoro unloaded - network stable, ~260-370 MB RAM freed", 2026-10-28).
- Nothing unloads the NLU model or the Qwen brain, so both stay resident for the rest of the session once started.
- The worst realistic case is the offline one: Kokoro and Moonshine are needed at exactly the same moment, because both are the fallbacks for losing the network.
- The planned RAM governor (`ram_budget.rs`), the `[RAM]` log sampler and the Hub "Memory" card do not exist. A search found neither the file nor any `[RAM]` line in the unified log, so the app cannot currently tell the owner where its memory is.

**Biggest UI defects**

- **Light theme is half built.** `theme.ts` only returns "light" for the literal value and defaults to dark, ignoring the OS preference. The newest surfaces (CodeRabbit panel, notification expand card, task chip, hand chip, captions) are hard-coded dark. In a rendered test the CodeRabbit panel stayed fully dark inside a light sidebar.
- **Dock buttons are invisible in light mode.** The shared `.sidebar-dock-btn` is white on transparent; its computed style on a white GitHub-dashboard header is `rgb(255,255,255)`. That is 1.05:1 contrast, and it affects the Architect, PR list, Annotate and Spatial views.
- **Pebble orb in light mode.** The pebble pouch is a hard-coded black SVG fill (`OrbFrame.tsx:253`) while the particles turn to black ink in light mode, so the orb is probably invisible. This is the owner's own configured style. It is read from code and not rendered.
- **The stage window is not sized to the monitor.** It is created at a fixed 1920x1080 and nothing resizes it. At the owner's 1080p/100 % setup this works by accident; on a 125 % or 150 % display the captions sit below the visible screen.

## How much RAM each part uses, and why the picture is incomplete

The only trustworthy baseline is one measurement day, 2026-10-16, when the release build was idle with the stage up: nexus.exe 94 MB resident, WebView2 browser 51, renderer 46, GPU 12 (but 83 MB commit), two utility processes 25, crashpad 4, for **235.6 MB resident and 268.9 MB commit in total**, from `docs/features/130-ram-usage-by-state-measured-and-estimated.md`. The same day recorded Kokoro stepping up from about 15 MB to 275-288 MB when the ONNX session loads and 339-350 MB after the first synthesis, then 368-379 MB after five syntheses, with 59-75 MB left after unload (docs 131 and 136). Those Kokoro numbers come from a unit-test process, which adds about 15 MB of harness overhead, and from a laptop on battery. Arena-off ONNX settings cut about 100 MB but made synthesis 34 % slower, so the docs reject them as a default; they should not be presented as shipped.

Windows trims the working set of idle, power-throttled processes, which is why nexus.exe shows only 16.5 MB private working set against 69.6 MB commit. For a ceiling check the resident or commit figure is the honest one, and Task Manager's default column will read much lower. The older 104-232 MB figures in AGENTS.md describe a pre-stage-overlay architecture and are superseded.

Three further caveats matter. First, the figures predate the late-October features (notification hub, Focus Mode, deploy watchers, task registry, Voice Lock enrollment and its speaker model), so any of them could have added resident state. Second, hand mode, extra windows, ghost mode, agent-watch, offline STT on the current default model, the Qwen brain and the CodeRabbit CLI have never been measured. Third, no one knows whether low-memory mode is applied to every dynamic window: `set_low_memory_mode` is called from the media-permission handler, which AGENTS.md says is registered for the hand window, so the Hub and Settings windows may not get it. The live check this session found no `nexus` or `python` process running; the six `msedgewebview2` processes present belong to Windows Search and were excluded. A 20-93 MB footprint for bare Node processes on the same machine supports, loosely, the 30-50 MB agent-watch estimate.

The best low-effort stack reductions are the ones already planned in doc 132 and never built. They are a compact pronunciation dictionary (the measured +125 MB dictionary cost is the largest single Kokoro step, with an estimated -100 to -115 MB saving), an idle unload for the NLU model, releasing the orb GPU process when hidden, and an in-process offline speech model so the offline case does not need a Python sidecar.

## How the memory feature works, and how well

**Mechanism.** Memcore keeps one SQLite database in memory (decrypted from a sealed AES-256-GCM blob, `memory/memcore.enc`, 843,808 bytes today) with an FTS5 text index. The key lives in Windows Credential Manager. Recall ranks by BM25 relevance (0.6), recency (0.2), use count (0.1) and a pinned bonus (0.1), plus a second pass through a hand-written synonym and stemming dictionary at 0.7x weight. Retrieval is lexical; there are no embeddings. Each cloud turn gets a "context pack" of at most 2,600 characters: a 1,400-character always-on profile of pinned user-told facts, up to 8 recalled facts and 3 episodes, all passed through the PII filter. Learning is deliberately conservative: an admit gate refuses secrets, a correction needs two sightings, a routine needs 3 sessions on 3 days, and model-suggested facts (the review feature, off by default) wait for the owner's approval. Forgetting works through age and count caps, a 3 % per idle day decay on unpinned mined facts, and a wipe that rotates the key.

**Resource cost.** RAM is negligible: about 0.85 MB of live database plus index, with transient copies of about 0.85 MB each during a write, an estimated 2-5 MB steady state. The costs are elsewhere. Every mutation re-serialises, re-encrypts and rewrites the whole file, and one cloud turn triggers an estimated 3-5 of those (two `mark_used` calls, `log_egress`, the episode write). `flag()` re-reads and re-parses settings.json from disk on every call, and about eight timers (30-60 s cadences, plus a 3 s keep-awake poll) give an estimated 0.3-0.5 wakeups per second that prevent deep idle on battery. The egress log keeps the full text of each cloud request for 7 days with an age cap but no row cap, so it is the only table that can grow without bound; that is an estimate of about 2 MB per 7 days at 100 turns a day, not a measurement.

**Quality.** Recall is good on the author's own tests and unproven in the real world. The synthetic 40-fact test gives 21/21 on direct questions, 19/19 on the dev paraphrases and 17/20 on held-out paraphrases (`docs/memory-core/07-memory-v2-baseline.md`). The same author wrote the synonym families and the questions, the three held-out misses are the "no shared word" cases (manager, nickname, hometown), and the CI assertions are far looser than the printed scores: `direct >= 19` and `para >= 1`. A collapse from 17/20 to 1/20 would not fail the build. On a 100-fact store the right fact reached the cloud pack 57/60 times with the profile on or off, so the pack's 8-fact cap and the 1,400-character profile bound recall more than ranking does. Corrections, routines, review and curator have unit and mutation tests but have never run on real data; the corrections replay produced 0 detections, which proves it stays quiet, not that it catches real corrections. One honesty issue: AGENTS.md and `docs/features/90` describe `habits.rs`, `memory_ipc.rs` and a top-level `profile.rs` as built, but none exists in the working tree, while the Memory page still tells the owner NEXUS "learns your habits". Why they are missing (renamed, removed, or lost in a working-tree collision) is not established.

**Privacy.** The design is sound for its stated scope (it stops disk theft and casual reads, not same-user malware). The risk worth knowing is that the profile of pinned facts is injected into every cloud turn by default and the egress log keeps a redacted copy of what was sent. It is visible on the Memory page but easy to overlook.

## What is wrong in each UI surface, in dark and light

**One root cause: seven token systems.** There is a clean token file (`theme/tokens.css`, `--nx-*`) but only five CSS files import it. The larger surfaces define parallel palettes: `--hx-*` in hub.css (2,523 lines, 204 hex literals), `--apple-*` in sidebar.css and architect.css, `--gh-*` in pr-list.css, plus `--kit`, `--hub`, `--stack`, `--tour`, `--hud`. They disagree on the same colours: card dark is `#141418`, `#15151b`, `#15151c` or `#121216` depending on the view. The theme is chosen four different ways: `:root[data-theme]`, bare `[data-theme]`, a `.theme--light` class on the GitHub dashboard, and `prefers-color-scheme` in the companion HUD. The HUD can therefore disagree with the Hub setting. Only five of the eight window entries call `initThemeSync()`, and orb-studio has no theme sync at all. Best practice is the opposite: three tiers (primitive, semantic, component), every role defined once with a light and a dark value, switched by one attribute plus `color-scheme` on `:root` ([MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/color-scheme); [DTCG stable spec](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)).

**Per-surface verdicts.** "Rendered" means checked in a browser harness; everything else is from reading the CSS.

| Surface | Dark | Light | Main defects |
|---|---|---|---|
| Orb capsule (classic) | OK | OK (has override) | amber hover glow breaks the white-only palette |
| Orb pebble (owner's style) | OK | **probably invisible** (black fill + black ink), INFERRED | fixed `#000` fill, no light rule; hit box registered as the 200x200 capsule while the pebble is 301x105 |
| Captions | OK | black pill by design; live caption has no background, so white text on light wallpapers is near 1.2:1 | no light variant, no live region |
| Spinner, task chip, hand chip, notify expand | OK | fixed dark, unthemed | no CSS variables; expand card hands off from dark to a light sidebar; chip edge 1.15-1.30:1 |
| Assistant view (responses) | OK | **likely broken**: 23 hard-coded white text colours on `#f8f9fa` (1.05:1), INFERRED | sidebar.css:240, 477, 728, 779 and others |
| CodeRabbit panel | OK | **broken, rendered**: stays dark | coderabbit.css has 0 `var()` and 0 theme rules |
| Command Hub home | OK (rendered) | OK (rendered) | faint text 2.8:1 and tertiary text 3.3:1 in light fail 4.5:1 |

**Dock buttons and chrome.** There are five dock-button implementations (the shared `.sidebar-dock-btn` at 9 px radius, the Hub's tokenised version at 8 px, StackView's `IconButton`, the Hub's full-width "Dock Left/Right" buttons, and arrow-key docking with no buttons on the Assistant view). All are 28 px, which meets WCAG 2.2's 24 px minimum ([WCAG 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). They use text glyphs (◧ ◨) with only a `title`, no `aria-label`. Press scale is `.94` in one and `.92` in another. Focus indication is nearly absent: `:focus-visible` appears in two files, while 14 CSS files declare `outline: none`. Scrollbars are hidden globally with `!important`. Spacing, radii (14 values from 2 to 18 px) and type sizes (26 distinct sizes, 64 declarations under 11 px) ignore the token scale, and the newest CSS ignores tokens entirely. The notes also flag stale comments (sidebar.css still says "Liquid Glass / DWM acrylic").

**Always-on overlay defects (P0 and P1).** The stage is created at a fixed 1920x1080 logical size with no position and nothing resizes it, so percentages are relative to a window that is not the screen on any other display; the owner's 100 % scale with an auto-hidden taskbar hides this. The hand chip and caption share the bottom centre and overlap by 7 px at 1080p and almost fully at 125 % with a visible taskbar. The spinner's size setting changes only its wrapper because the Lottie is fixed at 60x60, and the task-chip stack sits at a magic `top:112px` and overlaps the spinner at `loadingSize` 160. Three independent Escape handlers live on an unfocused, click-through window, so they probably never fire, and one of them cancels the whole turn when a pin is dismissed. Reduced-motion and forced-colours support exists only in the newest files; the pebble spring, orb slide and ghost rings ignore it. The `orbColor` setting is dead: the shader forces white. The toast has no icon, tag, group or expiry, so a stale "failed" toast can outlive a recovery. A conflict needs a live test: `NotifyExpand` positions itself through a React `style` prop, which the project's own notes say the stage CSP drops, and both cannot be true.

**Windows guidance supports solid panels.** Acrylic is reserved for transient light-dismiss surfaces and Mica is the opaque base ([Materials in Windows apps](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/materials)), so the app's solid-window rule is consistent. Windows also says darker surfaces mark less important layers in both modes ([Color in Windows](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/color)). The window-opacity gate passes ("13 CSS files, 0 violations") but it checks only registered panel selectors; the task chip, hand chip, guide bubble and captions are not registered.

## The prioritised plan

Nothing below is built; each phase lists files, a test and what stays unverified. Phases 1-5 are sequential in value; Phase 6 and Phase 7 can run in parallel with them.

**Phase 0: verify before building (half a day, owner-run).** Start NEXUS and capture the real idle tree; switch the Hub to Light and photograph the pebble orb, captions and CodeRabbit; run once on a 125 % display and read the `[ANIM] Stage overlay mounted` line; press Esc during a tour without clicking. This converts every INFERRED item above into a fact and prevents wasted work.

**Phase 1: token foundation and theme switching.** Extend `frontend/src/theme/tokens.css` into three tiers: primitives (neutral and accent ramps, status ramps), semantic roles (surface-app/panel/card/raised, text-primary/secondary/tertiary, border-subtle/strong, accent, focus-ring, danger/warning/success), and component aliases. Start with the lowest-risk dark values already in use (`#0a0a0c` background, `#141418` card) and darken or lighten steps by 3-5 lightness points per layer, as the design notes suggest; avoid pure `#000` with `#fff`. Rewrite `theme/theme.ts` to resolve "system" from `prefers-color-scheme`, set `data-theme` and `style.colorScheme` in a tiny inline head script in every HTML entry (including orb-studio and hand), add the `<meta name="color-scheme">` tag, and broadcast the choice across windows. Map the other namespaces (`--hx`, `--apple`, `--gh`, `--kit`, `--hub`, `--stack`, `--tour`, `--hud`) onto the semantic tokens as aliases first, so a view can be migrated without a visual change. Fix the contrast failures at the source: tertiary text in light (3.3:1), faint text (2.8:1 light, 3.8:1 dark), warning/success text on white. Test: a script computes WCAG ratios for every text/surface pair in the token file; screenshot baselines (Phase 6) show no unintended change. Unverified: the exact dark neutral values are a recommendation, not a sourced standard.

**Phase 2: dock buttons and chrome.** Create one `DockButton` and one `IconButton` component with SVG icons using `currentColor`, 32 px visual size, `aria-label`, `aria-pressed` where it toggles, hover/pressed/focus states from tokens, one press scale, and a tooltip with the shortcut. Replace the five implementations in `sidebar/unified.css`, `settings-sidebar/SettingsSidebarApp.tsx`, `architect/ArchitectApp.tsx`, `pr-list/PrListApp.tsx`, `sidebar/AnnotatePalette.tsx`, `sidebar/SpatialDashboard.tsx` and `sidebar/StackView.tsx`. Add one shared header row (40-48 px, title left, dock and close right, 8 px gaps). Add a global `:focus-visible` ring (2 px, 3:1) and remove the blanket `outline: none` rules; replace the global scrollbar hiding with a thin themed scrollbar. Give the Assistant view a visible dock control instead of arrow-key-only docking. Test: Playwright checks that every `button, [role=switch], [role=tab]` is at least 24x24 and has an accessible name; both-theme screenshots of every header.

**Phase 3: surfaces, one family at a time.** Order by damage: (a) CodeRabbit (`sidebar/coderabbit.css`, rewrite onto tokens, add light branch); (b) Assistant view (`sidebar/sidebar.css`, replace the 23 white text colours and black scrims with semantic tokens and drop the stale glass header); (c) the Architect, PR list and GitHub dashboard (retire `.theme--light/.theme--dark` in favour of `data-theme`); (d) the Hub sub-pages (`settings-sidebar/hub/hub.css`, 204 hex literals), then Setup, Settings and Orb Studio; (e) the companion HUD (remove the `prefers-color-scheme` path and the empty `.hud--light` rule). Standardise radii (4/8/12/full), spacing (4/8/12/16/24/32) and type (12/13/14/16/20 px, nothing under 11 px) by token. Decide and document one rule for the stage: either every HUD element follows the theme or all of them stay dark; the notes recommend the second for chips (solid dark reads on any wallpaper) but then the capsule should not flip either. Test: per-view both-theme screenshots; a hard-coded-colour lint that fails on any hex, `rgb()` or `hsl()` outside the primitives file.

**Phase 4: stage geometry and always-on overlays.** In `dyn_windows.rs` and `stage.rs`, size and position the stage to the primary monitor's physical rect on show, on display change and on scale change, and send `innerWidth/innerHeight` back so Rust can warn on mismatch. Replace the scattered coordinates with one layout owner that defines named slots: orb (top centre), spinner (top right) with the task stack anchored to the spinner's actual rect, caption at `workAreaBottom - 24 - height` with the hand chip stacked above it instead of on the same row, and sidebar-aware shifting when the CodeRabbit sidebar is open. Make the frontend report the real capsule rect through `stage_set_hitboxes` so the pebble's 301x105 shape is the clickable one; measure the spatial pin with `getBoundingClientRect` instead of the fixed 96x26 box. Fix the pebble: fill from a token with a light pair, so the orb stays visible in Light. Give the live caption the caption pill surface (distinguish user speech with a lighter border or a "You" tag). Make the Lottie fill its wrapper so `loadingSize` works. Move Escape ownership to Rust for dismissible overlays (as Ghost and Hand already do) and stop pin dismissal from cancelling a turn. Remove or implement the dead `orbColor` control; remove the amber hover glow; unify classic/pebble defaults (`commands.rs:2148` vs `store/assistant.ts:269`). Toast: add an icon, `Tag` and `Group` per entity key, an expiry matching the ledger lifetime, and replace the failed toast on recovery ([manage notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/manage-app-notifications)). Test: Rust unit tests for the rect maths at 100/125/150 % and 1366x768 / 2560x1440; a layout test asserting no two slot rectangles intersect; a live run on a scaled display. Unverified until run: the stage-size theory, toast behaviour under Do Not Disturb, and the CSP `style` question.

**Phase 5: accessibility.** Add one `prefers-reduced-motion` block in a shared stage stylesheet and a `useReducedMotion()` hook that pauses the Lottie and replaces the pebble spring and orb slide with a 150 ms fade (Apple's guidance is to substitute dissolves, not delete feedback; [Apple criteria](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/reduced-motion-evaluation-criteria/)). Extend forced-colours handling beyond the tour (borders and `currentColor` instead of shadows and tints; [MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)). Add one visually-hidden `role="status"` region mirroring the current caption and spinner state, and `role="alert"` for errors. Darken the tour pin gradient so 11.5 px white text reaches 4.5:1. Add a 1 px light border to dark chips so their edge passes 3:1 where it conveys a boundary. Test: axe-core in both themes, Narrator pass on one assistant turn.

**Phase 6: verification gates (build early, run always).** Add Playwright projects for light, dark, forced-colours and reduced-motion running `toHaveScreenshot()` over every window route, with animations disabled and dynamic content masked ([Playwright emulation](https://playwright.dev/docs/emulation)); the stage components need the Tauri runtime or a harness that mocks it, which does not exist for most of them today. Add the token-pair contrast script, a Stylelint rule banning raw colours outside the primitives file, an ESLint or grep check for colours in TSX inline styles, and register the task chip, hand chip, guide bubble and captions in `scripts/window-opacity-registry.json`. The exact Stylelint, axe and Playwright configuration keys were not verified in the research; confirm them against current versions.

**Phase 7: RAM measurement and memory improvements (parallel).** In order of value: (1) build the `[RAM]` sampler (per-process resident and commit every 60 s to the unified log) and a Hub "Memory" card, then record the idle tree, Hub open, hand mode and offline cases on the current build; this turns every ESTIMATED row above into MEASURED. (2) Apply low-memory mode to every dynamic window and measure Hub, Settings and Architect. (3) Add an idle unload to the NLU model. (4) Implement the compact pronunciation dictionary. (5) For memcore: wrap the cloud-turn writes in `Store::batch` (3-5 reseals to 1), cap egress by rows and shrink old rows to hashes plus a short preview, and cache settings.json in memory. (6) Merge the 30 s pollers into one scheduler tick that skips when idle or on battery saver. (7) Build a blind recall set written by someone else against messy real-shaped keys, and make the test fail if held-out recall drops below about 14/20. (8) Add a Memory-page view of which facts fit inside the 1,400-character profile. (9) Resolve the `habits.rs` mismatch by restoring the code or deleting the claims and the page text. Test: before/after `[RAM]` readings, a counter for `flush_now` calls per hour, and a Task Manager delta with `memcore` on and off.

## What stays unverified

Treat these as open: any current-build RAM value; the Hub, hand and offline figures; whether late-October features raised resident memory; the pebble-in-light failure and the Assistant-view white-on-white failure (code only); the Setup wizard, Architect, Hub sub-pages and tour overlay in either theme (not rendered); the entire production stage (cannot render outside Tauri; only two design harnesses were viewed); Escape behaviour on the unfocused stage; the toast and Do Not Disturb behaviour (Microsoft's own pages disagree on the urgent-scenario option and the code says "NOT verified on a device"); the stage-to-monitor mismatch at non-100 % scale; every memcore timing and RAM figure (estimates from code); the real store's contents and row counts (deliberately not read); and the design-system notes themselves. For those, the Material 3, Apple HIG and Primer pages returned nothing, the Fluent 2 guidance was not fetched, the dark-neutral hex values, spacing, radius and type scales are proposals rather than sourced standards, and the tooling names in Phase 6 are unconfirmed. Last, the research found about 17 sources for the design side only; the RAM and memory findings rest entirely on local repo files, code and one dated measurement day.

## Conclusion

The two halves of this report point at the same pattern: the project has good parts and good intentions, and they were never made to share one source of truth. Memory has a documented budget, a lazy-unload design and a plan for a governor, but no instrument reads the real number; the UI has a token file, a solid-window rule and a window-opacity gate, but most surfaces opt out of them. The cheapest, highest-value move is therefore measurement and unification, not new features: a `[RAM]` log line and a both-theme screenshot suite would each have caught most of the problems listed above months ago.

The second takeaway is a ranking the owner may not expect. The RAM ceiling is a minor risk for daily online use (about 236 MB idle) and a real one only offline, where a single decision, making the local speech and voice path cheaper, matters more than any tuning of memcore. Meanwhile light theme is the more urgent problem, because it is the owner's setting to switch and some surfaces become invisible or unreadable when they do. Phase 0 (a short owner-run check) will say within an hour how bad the pebble and Assistant-view cases really are, and should come before any code is touched.
