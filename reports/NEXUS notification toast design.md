# Extend NEXUS's notification hub into a five-second toast

NEXUS does not need a toast system built from zero: a typed notification pipeline (event ledger, Windows-native WinRT toast, click-to-sidebar transaction, expand animation) was committed in 82a71cc and is on `origin/main`, but it is wired for **GitHub Actions failures only**. The new request, a sidebar-wide, half-height, 5-second, per-app toast that deep-links into the real item, is best delivered by keeping that hub as the single source of truth and adding a **custom non-activating NEXUS toast window as the heads-up layer**, with the native Windows toast kept as the fallback and history channel. This must be an explicit owner decision, because `docs/changes/171` records that the owner rejected an in-app card and asked for the Windows notification centre. The data side is more mature than the UI side. Gmail, GitHub, deploys, WhatsApp, calendar and agent alerts all hold typed identifiers (thread id, run id, deployment id, jid, event id, cwd) one or two stack frames before `proactive_policy::submit` discards them. The hard parts are deep-link correctness (only GitHub URLs are verifiable today; Gmail, Render, Netlify and Supabase deep links are undocumented or unverified), focus-safe overlay mechanics (no existing non-activating helper), and privacy (mail and WhatsApp text on shared screens). A recommended architecture, phased plan, capability matrix, open decisions and risks follow at the end.

## What already exists, and the owner decision it collides with

The codebase map shows that all spoken or proactive alerts funnel through `proactive_policy::submit` and `submit_event`, which carry only `{id, text, urgency, event_key}` (`proactive_policy.rs:92-100`). Its `proactive:card` and `proactive:nudge` events have **no listener anywhere** in the frontend and sit in the `events-unmatched.txt` ratchet baseline. The real notification machinery is a second path. `notify_event.rs` defines a versioned `NotifyEvent` with provider, entity key, typed `Target`, privacy class (`Public|Redacted`), occurrence count and a 200-entry ledger that groups repeated failures. `Provider` already lists Gmail, Vercel, Render, Netlify and Supabase, and `Target` already has `Gmail`, `Deployment` and `Repo` variants with no producer (`notify_event.rs:19-26, 62-89`). `notify_hub.rs` records events and shows the native toast; `notify_native.rs` builds ToastGeneric XML with a `nexus://notify/open?event=<id>` launch argument; `notify_open.rs` allowlists provider URLs; `EventDetailView.tsx` and `NotifyExpand.tsx` render the in-sidebar detail and the expand animation. Only `github_watch.rs` calls `publish_github`; the deploy, mail, WhatsApp, calendar and agent producers stop at `proactive_policy` or `notify_brain::say`.

I verified the two points the earlier brief flagged against `origin/main` (f76ba4a, PR 43 merge). Commit 82a71cc is an ancestor of `origin/main` and all the `notify_*` files, `work_area.rs`, `NotifyExpand.tsx`, `EventDetailView.tsx` and `docs/changes/171` exist there, so the hub is current, not a stale local artefact. The codebase map's claim that `someone_is_here` does not exist is **wrong on main**: `proactive_policy.rs:460` defines `someone_is_here()` over `presence_from(idle_secs, locked)`, and it is already used to demote a Speak to a card when nobody is at the PC (`proactive_policy.rs:474`). The toast layer should reuse that presence signal instead of building a new one. The other map claim worth carrying with care: `notify_open.rs` deliberately returns `None` for Gmail and deployments (`provider_url`, with a test asserting `None` for a Gmail target), so those clicks currently do nothing useful.

The collision is with the owner's earlier decision. `docs/changes/171`'s "Redesign after the owner's first live look" section records that the owner rejected an in-app compact card and wanted the Windows notification centre plus a full-screen expand; `notify_native.rs` even states "Exactly one channel; there is no in-app card". The new request (a toast with sidebar width and half sidebar height, per-app content) is effectively an in-app card again, so it cannot be treated as a pure extension. Three reconcilable options exist. Option A keeps native only and enriches the XML (buttons, hero image); it respects the earlier decision and gets free Focus Assist and Notification Center behaviour, but the native toast cannot be forced to exactly 5 seconds, is limited to 3 text lines, 5 buttons and a 364x180 hero ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-content)), and cannot mimic a Gmail-style message view. Option B is custom-only, which gives full design control but must re-implement Do Not Disturb, accessibility, queueing and stage-independent reliability. **Option C, recommended, is a hybrid:** the custom NEXUS toast window is the 5-second heads-up while the user is present and unobstructed, and the existing native toast is the channel when a custom window would be wrong (Focus Session, fullscreen or presentation, meeting with content hidden, window creation failure, or the user choosing native-only). Microsoft itself documents suppressing a banner into Notification Center and adapting to Focus Sessions, which is exactly the fallback path ([Microsoft Learn UX guidance](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-ux-guidance)). Option C satisfies the new requirement without discarding the owner's notification-centre preference, as long as the owner confirms it.

## A focus-safe toast window can be built, but nothing in the repo does it yet

The window recipe is well precedented. New webview windows are `WindowConfig` constructors in `dyn_windows.rs`, created on demand and destroyed after use to reclaim roughly 250 MB of WebView2 process tree; `place_card()` (transparent, frameless, always on top, skip taskbar, `focus:false`) is the closest analogue. Registration requires a Vite rollup input and HTML entry, a capability JSON entry, an entry in `is_glass_window` (which also applies rounded corners and `WDA_EXCLUDEFROMCAPTURE`, desirable for a toast carrying mail text), and, because panel CSS must be solid, a line in `scripts/window-opacity-registry.json`. The size constants are easy: sidebar widths are 400 (settings, PR list), 520 (assistant default), 595 (CodeRabbit) in `commands::sidebar_geometry`, and `work_area::sidebar_rect` already does work-area and DPI math with tests. Because "the width of the normal sidebar" is not one number, the owner must pick it (520 is the default assistant sidebar; see open decisions).

The risk is focus theft. The codebase map found that `finish_sidebar` calls `set_focus()` and `SetForegroundWindow`, so the unified sidebar is **not actually non-activating today**, despite older notes, and no `WS_EX_NOACTIVATE` helper exists for Tauri windows. A toast that pulled focus would break dictation, Ghost and Hand Mode. The platform notes give the recipe: Tauri 2's `WebviewWindowBuilder` exposes `focusable(false)`, `focused(false)`, `always_on_top`, `skip_taskbar`, `transparent` and `shadow` ([docs.rs](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindowBuilder.html)), and tao added `with_focusable` in 0.34.1 ([tao release](https://v2.tauri.app/release/tao/v0.34.1/)). Raymond Chen warns that `WS_EX_NOACTIVATE` alone can leave a window unresponsive and that the cleaner route is answering `WM_MOUSEACTIVATE` with `MA_NOACTIVATE` so the window still receives clicks ([The Old New Thing](https://devblogs.microsoft.com/oldnewthing/?p=94295)). Showing should use `ShowWindow(SW_SHOWNOACTIVATE)` plus `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)` rather than Tauri `show()`; `early_orb.rs` and `window_tile.rs` already contain raw-HWND precedents. Whether WebView2's child HWND honours the `MA_NOACTIVATE` subclass is **unverified** and needs an on-device test that asserts `GetForegroundWindow()` is unchanged before and after the toast. Two traps to avoid: `shadow(true)` on an undecorated Windows window yields a 1px white border (draw the shadow in CSS inside transparent padding), and `set_ignore_cursor_events` is window-wide with an unresolved Windows report ([tauri#11461](https://github.com/tauri-apps/tauri/issues/11461)), so size the window exactly to the toast and avoid click-through tricks altogether.

Placement should come from the monitor's `work_area()` (taskbar may be on any edge and differs per monitor) with that monitor's scale factor, and the target monitor should be the one holding the foreground window, not the stage's primary-only monitor ([Old New Thing](https://devblogs.microsoft.com/oldnewthing/?p=43353)). The window must dodge three occupied zones: the right-docked sidebar (x = monitor width minus 520 minus 10), the bottom-centre caption slot, and the top-centre orb. A top-right or bottom-right toast with a rule to slide left when the sidebar is open is the least conflict-prone default; the native toast zone is the bottom right (`work_area.rs`: 364x96, margin 12). Hosting the toast inside the always-on `stage` overlay is the alternative and reuses the named-hitbox mechanism, but the stage is primary-monitor only, can be killed by `Ctrl+Alt+X`, drops React inline `style` props under its CSP, and a stage outage would silently lose the toast. That is another reason to keep native as the fallback channel. Before showing, call `SHQueryUserNotificationState`: states 1 (not present), 2 (busy), 3 (D3D fullscreen) and 4 (presentation) mean do not draw a banner, and a TOPMOST window can paint over borderless fullscreen video ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ne-shellapi-query_user_notification_state)). The repo does not query Focus Assist or this API anywhere today.

Duration needs a decision rather than a constant. Five seconds matches the Windows default banner time, but the user can raise it to as much as 300 seconds under Accessibility, stored as `MessageDuration` under `HKCU\Control Panel\Accessibility` ([Eleven Forum](https://www.elevenforum.com/t/change-how-long-notifications-stay-open-in-windows-11.819)). The design therefore uses `max(5 s, MessageDuration)`, pauses the timer on hover and keyboard focus, and relies on the ledger plus the native toast and sidebar detail as the persistent record, so a missed 5-second toast is recoverable. Reduced-motion and high-contrast handling should be CSS-level, and the page should use an ARIA live region; Narrator's behaviour on a non-focused WebView2 window is unverified.

## Deep links: GitHub is solid, the rest needs a fallback ladder

The click path should stay as the existing transaction: the toast carries only an opaque `ev_<24 hex>` id, Rust resolves it in the ledger, builds a URL from **typed fields never from notification text**, validates it with `is_safe_web_url`, and opens it with `open::that` (`command_executor.rs:385-416`). Doing this in Rust keeps the allowlist in one place and works without the sidebar open. A failed or unknown event falls back to the in-sidebar `EventDetailView`, which already exists.

For GitHub the REST API supplies everything: the jobs endpoint returns each job's `id`, `run_attempt`, `html_url` and `steps[]` with `number` and `conclusion` ([GitHub REST](https://docs.github.com/en/rest/actions/workflow-jobs)); review comments carry a required `html_url` ([GitHub REST](https://docs.github.com/en/rest/pulls/comments)). The recommended build is the job's own `html_url` with `#step:<n>:1` appended for the first failed step. That anchor is real (seen in a GitHub issue link) but undocumented, so a miss must degrade to the job page ([evidence](https://github.com/joshjohanning/github-actions-log-warning-checker/issues/3)). Today NEXUS parses only `id, event, conclusion, status, updated_at_ms` from each run and recovers the PR number with an extra API call (`github_watch.rs:20-69`, `coderabbit.rs:641-645`), even though `pull_requests`, `html_url`, `head_branch` and `display_title` are already in the list response; one call per failed run to the jobs endpoint adds the job id and failing step. Desktop alternatives are thin. The VS Code Pull Requests extension has a verified handler (`vscode://github.vscode-pull-request-github/open-pull-request-webview?uri=https://github.com/<o>/<r>/pull/<n>`) that fails silently on a bad number, and `checkout-pull-request` changes local state so it should not be used ([uri.ts](https://raw.githubusercontent.com/microsoft/vscode-pull-request-github/main/src/common/uri.ts), [vscode#275358](https://github.com/microsoft/vscode/issues/275358)); GitHub Desktop opens repos and branches, not Actions logs ([third-party](https://dev.to/zhensherlock/protocol-launcher-series-one-click-github-desktop-collaboration-4j29)). Conclusion: GitHub items always open in the browser; "view log in terminal" (`gh run view --log-failed`) is a secondary action at most. The log text for the toast preview comes from the jobs logs endpoint, a 302 to a one-minute plain-text URL, so it must be fetched immediately and never stored.

Gmail is the weakest link and the most requested. The Gmail API gives message id, thread id, account email, Message-ID-capable metadata, sender, subject and snippet, but NEXUS drops the account email at `fire_alerts(app, &fresh)` (`mailwatch.rs:382`) and has no URL builder. Google does not document any Gmail web URL format. Community evidence says `https://mail.google.com/mail/u/<N>/#all/<id>` works with the API message id and that the hex id in `#inbox/<id>` is the thread id ([Labnol](https://Labnol.org/internet/gmail-emails-have-permanent-web-address/6811/), [Limilabs](https://www.limilabs.com/blog/?p=1942)), that the new UI shows encoded ids that do not match legacy ids ([Stack Overflow, snippet only](https://backiee.wasmer.app/http_Stackoverflow_com/questions/50800330/gmail-api-does-not-support-new-thread-ids)), and that `u/<N>` depends on login order, with `?authuser=<email>` reportedly selecting the account ([Zenn](https://zenn.dev/ctxzz/articles/955a9c672ce089?locale=en)). The most robust id-independent form is a search for the RFC 822 Message-ID header (`#search/rfc822msgid:<id>`), which needs `metadataHeaders=Message-ID` added to the fetch (`google_io.rs:146-154`). The recommended ladder is `https://mail.google.com/mail/u/?authuser=<email>#search/rfc822msgid%3A<encoded>`, then `#all/<messageId>`, then `#inbox/<threadId>`, then the plain inbox. Combining `authuser` with a hash fragment is inferred and unproven; **it must be tested on the owner's real accounts and browser profiles** before the ladder's order is fixed. Browser-profile targeting (`chrome.exe --profile-directory=...`) is possible but only worth building if `authuser` fails. Opening Outlook or Windows Mail at a Gmail message is not possible (no documented per-message scheme), so "installed desktop app" for Gmail effectively means browser or PWA.

For deploys, only Vercel has a verified field: `inspectorUrl` on the deployment object ([Vercel API](https://vercel.com/docs/rest-api/reference/endpoints/deployments/get-a-deployment-by-id-or-url)), which the NEXUS parser (`deploy_watch.rs:73-130`) currently ignores. Render's deploy object has no dashboard URL ([Render API](https://api-docs.render.com/reference/retrieve-deploy)); Netlify's documented dashboard paths are project and team settings, and `admin_url` points at the site ([Netlify docs](https://docs.netlify.com/api-and-cli-guides/api-guides/get-started-with-api/)); Supabase uses `https://supabase.com/dashboard/project/<ref>/...` ([Supabase docs](https://supabase.com/docs/guides/monitoring-and-debugging/logs.md)). Deploy-page patterns for Render, Netlify and Supabase are constructible from ids NEXUS already holds but are unverified, so the rule is: use the verified API URL where it exists, construct the rest, and fall back to the service or project page, never a guess that 404s silently. Calendar is easy: the API's `htmlLink` opens the event, but `CalendarEvent` does not store it (`google/types.rs:149-157`), and `hangoutLink` gives the Meet join URL ([Calendar API](https://developers.google.com/workspace/calendar/api/v3/reference/events)). WhatsApp can open a chat only: `whatsapp://send?phone=<digits>` is already used in `wa_open.rs`, `wa.me` is the browser fallback ([u2l.ai](https://u2l.ai/blog/whatsapp-click-to-chat-link)), and no scheme targets a specific message; the alert path carries a jid with no phone mapping. Coding agents have no documented session-focus URL; the realistic click is to focus the window whose process and title match the agent's stored `cwd` (`agent_hooks::last_cwd`), reusing `wait_and_focus_app`, with "open the project in the IDE" as the fallback.

App detection should be minimal. For a browser, let the OS default handle `https` via `open::that`; the default-browser ProgId is under `HKCU\...\UrlAssociations\https\UserChoice` and must be read but never written ([Firefox source](https://searchfox.org/firefox-main/source/browser/components/shell/WindowsUserChoice.h)). Probe protocol registration (`HKCR\whatsapp`, `vscode`, `x-github-client`) only for the few schemes NEXUS actually prefers, and fall back to the browser URL when absent. The repo has no installed-app helper beyond `app_registry`.

## Per-app content must mimic information, not interfaces

The toast's face is a NEXUS component with a per-source layout; it should reproduce each app's information structure, not its pixels. The legal notes found that vendor brand pages restrict logos, not generic layouts: GitHub forbids implying endorsement, altering logos, or using them as your own icon ([GitHub brand](https://brand.github.com/foundations/logo)); Vercel allows truthful descriptive use but not greater prominence than your own marks ([Vercel brand](https://vercel.com/geist/brands)); WhatsApp and Google describe no integration allowance for their marks ([Meta](https://www.meta.com/brand/resources/whatsapp/whatsapp-brand/), [Google](https://about.google/brand-resource-center/brand-elements)). No source addresses trade dress or copyright of UI layouts, and Netlify, Render and Supabase guidelines were not retrieved, so the safe recipe is NEXUS's own typography and card, a small neutral source chip with the app name in text and a generic icon (envelope, branch, rocket), generic red/green status colours, and no vendor logos (a Gmail red-M envelope, the Invertocat, the WhatsApp glyph) unless the owner obtains permission. Octicons are MIT but the GitHub marks inside the set stay trademarks (reading of the licence, not a stated rule) ([Octicons LICENSE](https://raw.githubusercontent.com/primer/octicons/main/LICENSE)). This is not legal advice and the owner should confirm if any logo is wanted.

The content hierarchy, built on the Windows and Android anatomy (identity, title, one-line body, sender image, at most a few actions) ([Android](https://developer.android.com/develop/ui/views/notifications/build-notification)), becomes this. Mail: sender initial circle and name, bold subject, one-line snippet, "Mail" chip, Open and Mute sender actions (reusing `mailwatch::mute_sender`). GitHub PR or CI: status chip, `repo · branch` or PR title, failing job and step with the first annotation (`file:line` plus message, per GitHub's annotation fields ([GitHub Docs](https://docs.github.com/en/actions/using-workflows/workflow-commands-for-github-actions))), duration, "View run" action. Deploy: status chip, project and environment, branch and short SHA, one-line error on failure, "View logs". WhatsApp: contact name and count, "New message" with no text by default (the project already restricts alerts to the sender and keeps `memcoreWhatsappSpeak` off). Calendar: title, start time, location or Meet join, "Join" action. Agent: agent label, project folder name, "needs your input" or "finished", "Focus". At half the sidebar's height the card has room for about three lines plus actions, so the preview strings should be generated locally (title at most 120 characters, preview at most 240, matching the existing `NotifyEvent` limits) and **never** sent to a cloud model; `memcoreMailPlain` stays off by default.

Grouping and rate limits should reuse what exists and avoid a third dedupe layer disagreeing with the first two. `proactive_policy` already dedupes by id and event key with 5-minute and 2-minute cooldowns and caps non-critical speech at six per hour; `notify_brain` collapses state changes (first failure once, recovery once, still-failing after 6 hours); the ledger groups repeats with an occurrence count. The toast should hang off the same decision the brain makes (`Decision::Say`), show at most one toast at a time, replace in place on the same entity key ("+3 more"), and queue the rest silently. The research literature supports matching attention capture to content utility ([Gluck et al., CHI 2007](https://www.interruptions.net/literature/Gluck-CHI07.pdf)), but no authoritative "ideal duration" exists, so the failure-gets-longer idea (8 to 10 seconds) is a suggestion, not a finding. Sound should be off except for Critical and always off while screen sharing.

Privacy is the area most likely to cause real harm. Apple and Android both say not to put private content in notifications others might see, and Android offers a redacted public version ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/managing-notifications.md), [Android](https://developer.android.com/develop/ui/views/notifications/build-notification)). NEXUS has the hooks (`PrivacyClass::Redacted` drops the preview in the ledger) but no producer uses them and `publish_github_with` never consults `MeetingState`. The design adds three content modes: Normal (sender, subject, one-line snippet), Private (sender and subject only) and Hidden (source chip and count only), switched automatically to Private or Hidden on meeting detection, fullscreen or presentation state, or a user "hide content" setting, and heuristically masking OTPs, password-reset links and bank or UPI keywords as "Security message". Apply `WDA_EXCLUDEFROMCAPTURE` to the toast window; Microsoft states it is not a security feature and it does nothing before Windows 10 2004 or over Remote Desktop ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/desktop/api/winuser/nf-winuser-setwindowdisplayaffinity), [IOActive](https://www.ioactive.com/the-drm-flag-that-isnt-drm/)). On the Gmail side, Google's restricted-scope Limited Use rules prohibit transferring data except to provide visible user-facing features and prohibit permanent copies beyond caching rules ([Google policy](https://developers.google.com/gmail/api/policy)). A local, in-memory, short-expiry toast pipeline fits; sending snippets to a cloud model or persisting bodies does not. Whether Google would treat a transient toast as storage is not addressed by the policy text reviewed.

## Recommended architecture

Keep `notify_event`/`notify_hub` as the single typed source of truth and add a channel decision stage between "event recorded" and "delivered". The flow is: producer (Gmail, GitHub, deploy, WhatsApp, calendar, agent) emits a typed event to the hub; the hub applies privacy classification and the existing dedupe; a new `toast_policy` decides `CustomToast`, `NativeToast`, or `HistoryOnly` from presence (`someone_is_here`), meeting, `focus_mode::paused()`, `SHQueryUserNotificationState`, urgency and user settings; the custom channel shows one non-activating `notify-toast` window carrying only the event's display payload; a click or button calls a Rust command with the opaque event id, which builds the URL from the typed target and opens it; the native toast is shown when the policy says so or window creation fails, with the existing `nexus://notify/open` activation. Events stay in the ledger so a missed toast is recoverable via the sidebar detail, and the ledger should gain persistence (a sealed `entity_state`-style table) because it is in-memory today and a click after restart reads "unavailable".

## Open decisions for the owner

1. Reconcile with the earlier rejection of an in-app card: approve Option C (custom heads-up plus native fallback), choose native-only enrichment (A), or custom-only (B).
2. The toast width: "the sidebar's width" is 400, 520 or 595 depending on view; pick 520 (assistant default) or a view-matched rule, and confirm half of the sidebar's height (the sidebar is 1040 maximum, so about 520) is intended.
3. Screen position and collision rule with the right-docked sidebar, caption and orb; which monitor (foreground window, cursor, or primary).
4. Duration policy: strict 5 seconds or `max(5 s, Windows setting)`, hover pause, longer for failures, and whether Critical items stay until dismissed.
5. Which sources get a toast by default, and which stay history-only (success events, WhatsApp, low-priority mail).
6. Privacy defaults: show snippets in Normal mode or default to Private; behaviour during meetings and fullscreen; whether WhatsApp ever shows message text.
7. Whether vendor logos are wanted (permission risk) or neutral chips only; whether to seek legal review.
8. Gmail account handling: trust `authuser`, or build browser-profile targeting.
9. Sound policy and whether Yes/No offer buttons (for example "Shall I start?" slot offers) belong on the toast, which would need a new path because the offer arms only after speech.
10. Ledger persistence: approve a sealed on-disk table so clicks survive restart.

## Risks

The highest risk is **focus theft**: nothing in the repo shows a verified non-activating WebView2 window, and WebView2's child HWND may behave differently from the subclass assumption, so the feature cannot be called done without a device test. Close behind is **owner-decision regression**: shipping a custom card without sign-off repeats the exact conflict recorded in `docs/changes/171`. Deep-link risk is concentrated in Gmail, where every URL form is undocumented and the new UI's ids may not match legacy ones, and in Render, Netlify and Supabase paths, which are unverified; a wrong link opens a login chooser or a 404 and erodes trust in the toast. Privacy risk is real: mail and WhatsApp content on a shared screen, native Action Center persistence of text, and `WDA_EXCLUDEFROMCAPTURE` being a mitigation rather than a guarantee; the stage is deliberately not capture-excluded. Reliability risks include the in-memory ledger (lost on restart), the stage's primary-only and kill-switch weaknesses, three dedupe layers that can double-notify or suppress a real repeat, the GitHub-mail path that cannot form a numeric run id, and the native toast being unverified on this device (Action Center clicks after a restart do nothing without a COM activator). Process risks follow the repo's habits: new settings must be added to `NexusSettings` or `save_settings` drops them, the ratchets (IPC, dead code, opacity, hard-coded colours) only shrink, a new window needs its Vite input and capability or it is blank in release, window-creating commands must be async, and concurrent edits to `orchestrator.rs` and `intent_parser.rs` mean patches must stay narrow. Finally, this report rests on a read-only code survey and web research with several snippet-level sources; no unit of it was executed, and the unsourced items (Gmail `authuser` plus hash, deploy URL shapes, Narrator behaviour, tao `with_focusable` internals) are flagged as unverified above.

## Conclusion

The central insight is that the toast is a presentation problem sitting on top of an already-built event contract, and that the contract, not the window, is where most of the remaining work and risk lies: typed targets exist for five providers with no producers, and link builders exist for only one. Building the data and link plumbing first (phases 1 and 2) delivers value even if the owner ultimately keeps the native toast, which makes the custom window a reversible, last-mile choice rather than a foundation.

The owner's earlier preference for the Windows notification centre is best treated as a constraint to honour, not an obstacle to override: a hybrid that uses the custom card only when the user is present and unobstructed, and native otherwise, keeps Focus Assist, history and accessibility semantics while delivering the half-height, per-app, 5-second experience. The two things nobody can settle from documents are whether a WebView2 toast can truly stay non-activating and whether the Gmail `authuser` link lands on the right message in the owner's real browser profiles; both are short device experiments and should be run before the UI is polished.
